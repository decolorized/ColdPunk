# Матрица соответствия ТЗ

Построчная сверка требований ТЗ «Аппаратный кошелёк Monero» версии 4.0 с
тем, что реально есть в репозитории.

> **Устарело после ТЗ 2.0 и task2 (2026-09-29).** Разделы 3.3–3.6 и 10
> (USB MSC, MTP, флоппи, Composite, SCSI INQUIRY, autorun) больше не
> относятся к проекту: этот код удалён, каналы обмена — SD-карта, QR и
> USB-линк для программы на ПК (`docs/usb_link_protocol.md`). Противоречие
> C-1 закрыто: legacy passphrase реализован как seed offset Monero.
> Хранение ключей дополнено паролем устройства (`docs/device_password.md`).
> Матрица по новому ТЗ ещё не составлена.

## Как читать статус

| Статус | Что означает |
| :--- | :--- |
| **реализовано** | требование выполнено и это видно из содержимого репозитория (константа, структура, файл), проверять на устройстве нечего |
| **требует проверки** | контракт (функция, тип, макрос) существует в заголовке, но работоспособность подтвердить нельзя: код не дописан, тестов нет, на железе не проверено |
| **частично** | часть требования покрыта контрактом, часть — нет, либо есть известное отклонение |
| **не реализовано** | контракта нет |
| **вне объёма** | ТЗ само выносит пункт за рамки текущей версии |

## Состояние проверки

Первая редакция этого документа составлялась по замороженным заголовкам,
до того как появился код. Ниже — статус после того, как код написан
и прогнан.

| Что проверено | Результат |
| :--- | :--- |
| Функции контракта (25 заголовков) | 279 объявлено, 279 реализовано |
| Хостовые наборы тестов | 18 наборов, **42 198 проверок, 0 ошибок** |
| Те же наборы под ASan + UBSan | 0 ошибок, 0 диагностик |
| Хостовая заглушка HAL | компилируется чисто |
| Прошивка под Arduino IDE | **не собиралась** — в этом окружении нет ESP32-ядра |
| Проверка на железе | **не проводилась** |
| Кампания на stagenet (ТЗ 13.6) | **не проводилась** |

**Что это значит для статусов.** «Реализовано» ниже означает одно из двух:
требование видно прямо в репозитории, либо оно покрыто хостовым тестом,
который проходит. Для кода, который физически нельзя собрать здесь — драйверы
дисплея и сенсора, TinyUSB, LVGL, eFuse/NVS — статус «требует проверки»
сохраняется даже там, где код написан целиком. Это примерно 40 % проекта, и
никакая проверка вычиткой этого не заменяет.

**Чего проверка не покрывает даже там, где тесты зелёные.** Совместимость с
реальным Monero подтверждена сверкой с эталонными реализациями (векторы
CryptoNight, `crypto-ops.c` из Monero для `hash_to_point`, эталонный кодер
Blockchain Commons для UR, `qrcodegen` для QR), но ни один файл ещё не прошёл
через настоящий Feather или Monero GUI.

### Отклонение 2.2-A: пины

Таблица ТЗ 2.2 приводит номера GPIO классического ESP32 (`TFT_MOSI` 23,
`TFT_SCK` 18, `TOUCH_SDA` 21 и т.д.), тогда как ТЗ 1.4 предписывает
ESP32-S3. На S3 этих выводов либо нет, либо они strapping. Кроме того, в
таблице ТЗ `CAM_PIN_SIOC` = 39 совпадает с `TOUCH_INT` = 39 — прямой
конфликт внутри самого ТЗ. `boards/es3c28p.h` содержит пересчитанные под S3
значения и объясняет это в шапке файла.

### Отклонение 2.2-B: камера на референсной плате

ТЗ 2.2 задаёт `HAS_CAMERA 1` и полную распиновку камеры для ES3C28P.
`boards/es3c28p.h` ставит `HAS_CAMERA 0` и все `CAM_PIN_*` в `-1`.
Последствие: на референсной плате **приём** QR недоступен (показ QR
работает). Это меняет объём этапа 8.

### Противоречие C-1: схема passphrase для Monero legacy

`src/monero/mnemonic.h` определяет:

> Legacy seeds: the passphrase is folded in as
> `spend = sc_reduce32(keccak256(seed || passphrase))` when passphrase != ""
> so an empty passphrase reproduces the plain Monero seed exactly.

Monero применяет passphrase к legacy-seed иначе — как «seed offset»:
`key = sc_add(recovery_key, hash_to_scalar(passphrase))`. Схемы не
эквивалентны.

Последствия:

- кошелёк **без** passphrase совместим полностью (обе схемы вырождаются в
  обычный seed);
- кошелёк **с непустым** passphrase, созданный на устройстве, **не
  воспроизведётся** в `monero-wallet-cli` с той же фразой и тем же
  passphrase;
- это делает устройство единственным способом восстановить такой кошелёк —
  что противоречит самому смыслу seed-фразы как резервной копии.

ТЗ 5.2 схему не задаёт, так что формально нарушения ТЗ нет, но риск для
пользователя реальный. Решение требуется до релиза: либо перейти на схему
Monero, либо явно и громко предупреждать пользователя. Статус: **частично**.

### Противоречие C-2: шифрование NVS под Arduino IDE

ТЗ 8.1 требует опции ESP-IDF `CONFIG_NVS_ENCRYPTION=y`, а ТЗ 1.3 требует
Arduino IDE. Arduino IDE поставляет предсобранные библиотеки IDF, и изменить
sdkconfig из неё нельзя. Два требования ТЗ несовместимы без пересборки
библиотек.

Выбранный компромисс: seed шифруется приложением
(`mw_seal`/`mw_unseal`, AES-256-GCM на ключе из eFuse HMAC), а в NVS кладётся
уже зашифрованным (`encrypted_seed[64]`, `seed_iv[16]`, `seed_tag[16]`).
Сам контейнер NVS при этом не зашифрован — метаданные (имена кошельков,
restore height, настройки) лежат открыто.

Статус: **частично**. Варианты и их цена — в `docs/build_arduino.md` §5.

### Открытый вопрос: размещение секретов

Заголовки не фиксируют, что расшифрованные ключи и passphrase обязаны
лежать во внутреннем SRAM, а не в PSRAM. PSRAM у ESP32-S3 — внешний чип, и
его содержимое снять физически проще. Требование в ТЗ отсутствует, контракта
нет. Статус: **не реализовано** (как явная гарантия); требует решения при
реализации `session.h`.

### Противоречие C-4: длины magic-строк

| Формат | ТЗ | Фактическая длина строки | В коде |
| :--- | ---: | ---: | ---: |
| `outputs.bin` | 21 | 21 | 21 ✓ |
| `keyimages.bin` | 26 | **24** | 26 ✗ |
| `unsigned_tx_set.bin` | 24 | **22** (+1 версия = 23) | 22 ✓ |
| `signed_tx_set.bin` | — | 20 (+1 версия = 21) | 20 ✓ |

`"Monero key image export"` — 23 символа, плюс `\003` = 24 байта. ТЗ 9.2
указывает 26, и `MW_MAGIC_KEYIMAGES_LEN` = 26 повторяет эту ошибку.
С неверной длиной сравнение magic залезет в поле IV и корректный файл

Ошибка ТЗ 9.3 (24 вместо 22) в коде уже исправлена.

### Противоречие C-5: ключ подписи файлов

Комментарий `file_formats.h` говорит: «a Schnorr signature over
keccak256(iv || ct) under the account's spend (or view) key». Monero в
`encrypt_with_view_secret_key` подписывает **view key**. Если реализация
выберет spend key, файлы будут несовместимы с Feather и Monero GUI.
Формулировку надо уточнить до однозначной. Статус: **требует проверки**.
