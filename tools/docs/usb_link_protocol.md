# USB-линк: Serial и HID (протокол 2)

ТЗ 2.0 §1.3, §3.3, §3.8; task2 пп. 2, 3, 11, 12; задача 3 пп. 1.1, 3, 6.
Один протокол «запрос — ответ» плюс события устройства поверх двух
транспортов: стандартного `Serial` ядра Arduino и vendor-specific HID с
64-байтовыми отчётами. Программа на ПК — только курьер: кладёт входной файл
в **inbox** устройства и забирает результат из **outbox**; все
преобразования делает устройство и только после подтверждения на его
экране. Seed, passphrase и private spend key по линку не ходят никогда;
private view key уходит только по запросу ПК **и** после подтверждения
кодом на устройстве.

Реализация: `src/transfer/link.h`, `link.c` (ядро, компилируется в хостовые
тесты), `src/transfer/usb_link_arduino.cpp` (транспорты),
`src/ui/flows.cpp` (что устройство делает с файлами и запросами),
`tools/mwlink/mwlink.py` (библиотека и CLI), `tools/mwlink/mwlink_gui.py`
(фронтенд), `tools/mwlink/link_sim.c` (имитатор устройства для тестов ПК),
`test/test_link.c`.

---

## 1. Транспорты и настройки Arduino IDE

Прошивка собирается при **любой** комбинации Tools → USB Mode / USB CDC On
Boot (task2 п. 3). Недоступный транспорт просто не объявляется в INFO.

| USB Mode | CDC On Boot | `Serial` = | Serial-линк | HID | Консоль UART0 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| USB-OTG (TinyUSB) | Enabled | USB CDC | да | да | да (Serial0) |
| USB-OTG (TinyUSB) | Disabled | UART0 | да, по UART0 | да | нет — UART0 занят протоколом |
| Hardware CDC and JTAG | Enabled | USB-Serial/JTAG | да | нет | да (Serial0) |
| Hardware CDC and JTAG | Disabled | UART0 | да, по UART0 | нет | нет |

Рекомендуемая связка для ES3C28P: **USB-OTG + CDC On Boot Enabled** — COM-порт
и HID на одном кабеле, консоль на UART0 (GPIO43/44, `MW_SERIAL_USE_UART0`).

## 2. Сообщение

Одинаково для обоих транспортов. Все числа little-endian.

| Смещение | Размер | Поле |
| ---: | ---: | :--- |
| 0 | 2 | magic `"MW"` |
| 2 | 1 | `cmd` |
| 3 | 1 | `arg` |
| 4 | 4 | `len` payload, не более 262144 (256 КиБ) |
| 8 | `len` | payload |
| 8 + `len` | 4 | CRC32 (IEEE, как в zlib) по байтам `[0, 8 + len)` |

256 КиБ хватает на экспорт выходов примерно из 1000–3000 записей и на
транзакцию с 32 входами. Файл больше лимита ПК отклоняет сам.

## 3. Кадрирование

**Serial**: COBS(сообщение) + `0x00`. Нуль внутри кадра невозможен и служит
для ресинхронизации. Скорость 115200 значима только для UART0.

**HID**: usage page `0xFF00`, report ID `0x01`, 63 байта данных
(1 + 63 = 64 байта на шине). Первый отчёт `"?##"` + 60 байт, следующие
`"?"` + 62 байта, последний дополнен нулями (формат Trezor v1).
Приёмники (устройство и `mwlink.py`) начинают кадр только с отчёта
`"?##MW"`: каждое сообщение начинается с magic, а данные продолжения сами
могут начинаться с `"##"` (у случайных данных это 1 отчёт из 65536; раньше
такой отчёт обрывал файл, и ПК 60 с ждал ответа). Формат на шине не менялся.
`mwlink.py` хранит недособранное сообщение между чтениями и открывает HID в
неблокирующем режиме с таймаутом чтения не меньше 1 мс.

## 4. Команды

| Запрос | `cmd` | `arg` | payload | Ответ |
| :--- | ---: | :--- | :--- | :--- |
| PING | `0x01` | эхо | эхо, до 256 байт | PONG `0x81` |
| INFO | `0x02` | — | — | INFO `0x82`, 128 байт (§6) |
| PUT | `0x03` | вид файла или `0xFE` (авто) | файл | ACK `0x83`, `arg` = вид, под которым файл принят |
| GET | `0x04` | вид файла 0..4 | — | FILE `0x84`, payload = файл |
| STATUS | `0x05` | — | — | STATUS `0x85`, 48 байт (§5) |
| CLEAR | `0x06` | вид или `0xFF` | — | ACK `0x83` (чистит outbox) |
| REQ | `0x07` | 1 адрес, 2 данные view-only | — | ACK `0x83` |

Виды файлов:

| Вид | Что | Кто создаёт |
| ---: | :--- | :--- |
| 0 | «Monero output export» (Feather: export outputs) | ПК |
| 1 | «Monero key image export» | устройство |
| 2 | «Monero unsigned tx set» | ПК |
| 3 | «Monero signed tx set» | устройство |
| 4 | данные кошелька по запросу REQ, JSON | устройство |

**PUT с `arg = 0xFE`** — основной режим фронтенда: устройство само
определяет вид по содержимому (magic), имя и расширение файла на ПК роли не
играют (задача 3 п. 6). ACK возвращает определённый вид.

Устройство принимает PUT только когда открыт кошелёк (§5, состояние 2) и
только виды 0 и 2; всё остальное отклоняется с объяснением:

| Код ERROR | Имя | Когда |
| ---: | :--- | :--- |
| 1 | bad command | неизвестная команда или REQ с неизвестным `arg` |
| 2 | bad file kind | `arg` не вид файла |
| 3 | too big | payload больше лимита |
| 4 | not ready | GET из пустого outbox |
| 5 | no memory | нет памяти под файл |
| 6/7/8 | crc / bad length / bad magic | повреждённый кадр |
| 9 | unrecognised file | PUT авто: не выход и не неподписанная транзакция; текст объясняет, что это за файл |
| 10 | busy | устройство занято предыдущим файлом (состояние 3: файл на экране) или запросом; текст: «the device is busy with the previous file: finish or cancel it on the device» |
| 11 | not accepted | устройство заблокировано, кошелёк не открыт или этот вид файла сейчас не принимается; текст объясняет |

Payload ошибки — текст (UTF-8), фронтенд показывает его как есть.

### REQ — запрос данных кошелька

`REQ 1` — адрес, `REQ 2` — данные для view-only кошелька Feather (адрес,
private view key, restore height). Устройство показывает запрос на экране:
адрес отправляется после «Да», view key — только после ввода показанного
четырёхзначного кода. Ответ появляется в outbox вида 4:

```json
{
  "version": 1,
  "wallet": "borya",
  "network": "mainnet",
  "address": "4...",
  "restore_height": 3100000,
  "view_key": "…только для REQ 2…"
}
```

Отказ пользователя — outbox остаётся пустым, в лог уходит строка
«request declined on the device».

### Событие LOG `0x90` (устройство → ПК, без запроса)

`arg` — уровень: 0 progress, 1 error, 2 info, 3 debug; payload — строка
`[тег] текст` без перевода строки. Устройство шлёт события каждому
транспорту, с которого за последние 30 с приходил запрос (фронтенд опрашивает
STATUS раз в секунду).

- Уровни 0–2 идут всегда: что происходит с устройством (разблокировано,
  открыт кошелёк, получен файл, ожидание подтверждения, готов результат) и
  ошибки с подробной причиной («outputs: exported by a different wallet»,
  «tx 1 input 2 (0.5 XMR): key image not synchronised …», «the change address
  is not an address of this wallet …»).
- Уровень 3 — только в отладочном режиме (Настройки → Отладочный лог):
  подробности разбора (индексы выходов, подадреса, число входов/выходов,
  размеры), трассировка интерфейса.
- Секретов в логе не бывает по правилу `src/hal/log.h`: ни ключей, ни seed,
  ни passphrase, ни key images.

## 5. STATUS

| Смещение | Поле |
| ---: | :--- |
| 0 | `u32 inbox_len[5]` |
| 20 | `u32 outbox_len[5]` |
| 40 | `u8` состояние: 0 заблокировано, 1 меню, 2 кошелёк открыт, 3 занято |
| 41 | `u8` ожидающий запрос REQ (0 — нет) |
| 42 | `u8` маска видов, которые PUT сейчас примет |
| 44 | `u32` счётчик событий (растёт при каждом изменении состояния и новом результате) |

## 6. INFO

| Смещение | Поле |
| ---: | :--- |
| 0 | `u8` версия протокола (2) |
| 1 | `u8` возможности: бит 0 serial, 1 HID, 3 авто-PUT, 4 REQ |
| 2 | `u8` состояние (как в STATUS) |
| 3 | `u8` сеть: 0 mainnet, 1 testnet, 2 stagenet |
| 4 | `u32` максимальный payload |
| 8 | `u8` число кошельков (0, пока устройство заблокировано) |
| 9 | `u8` разблокировано |
| 10 | `u8` открыт вариант кошелька с passphrase |
| 11 | `u8` число видов файлов (5) |
| 12 | `char[16]` версия прошивки |
| 28 | `char[32]` имя платы |
| 60 | `char[32]` имя открытого кошелька (пусто, если не открыт) |
| 92 | `u8` причина последнего сброса: 0 неизвестно, 1 включение питания, 2 вывод RESET, 3 программный перезапуск, 4 сбой (panic), 5 interrupt watchdog, 6 task watchdog, 7 другой watchdog, 8 выход из deep sleep, 9 просадка питания, 10 USB/JTAG, 11 другое |
| 93 | `u8` последний сбой: операция (1 подпись, 2 key images, 3 открытие кошелька, 4 экспорт) |
| 94 | `u8` последний сбой: этап (1 загрузка, 2 проверка, 3 ключи, 4 CLSAG, 5 Bulletproofs+, 6 шифрование результата, 7 выдача) |
| 95 | `u8` флаги: бит 0 — байты 93–94 описывают сбой, бит 1 — байты 96–97 измерены |
| 96 | `u16` минимальный свободный стек криптозадачи на последнем этапе перед сбоем, байт |
| 98 | 30 байт — резерв |

Пока устройство заблокировано (идёт игра или ввод пароля), INFO не сообщает
ни имена, ни число кошельков, ни байты 93–97 (нули). Причина сброса (байт 92)
сообщается всегда: это общий код, о кошельке он ничего не говорит.

Сведения о сбое — «хлебная крошка» в RTC-памяти (`mw_hal_crumb_set`), которую
криптозадача обновляет по этапам; она переживает panic и сброс watchdog, но не
выключение питания, и содержит только номера операции и этапа и цифру стека,
никаких данных. Дампы памяти (core dump) не включаются: в них попали бы ключи
со стека.

## 7. Сценарий обмена (Feather)

1. Кошелёк открыт на устройстве (главное меню → Кошельки → кошелёк →
   passphrase, если есть). STATUS: состояние 2, маска `0x05`.
2. Feather сохраняет «export outputs» в папку обмена фронтенда, например
   `borya-view2_1789637203_outputs`.
3. Фронтенд (наблюдение за папкой или «Отправить файл…»): `PUT 0xFE` → ACK
   `arg = 0`. Файл, найденный наблюдением, переносится в `sent/`; файл,
   выбранный вручную, остаётся на месте и наблюдением повторно не
   отправляется. Пока файл на экране устройства (состояние 3), следующий PUT
   получает ERROR 10 busy.
4. Устройство проверяет файл (подпись view key этого кошелька, ключи в
   заголовке, структуру), спрашивает «Сгенерировать key images для N
   выходов?», считает и кладёт результат в outbox 1.
5. Фронтенд по STATUS видит `outbox_len[1] > 0` → `GET 1` → сохраняет
   `borya-view2_1789638364_keyImages` → `CLEAR 1`. До CLEAR файл остаётся в
   outbox: обрыв кабеля стоит одного повторного GET.
6. Подпись: `1789839233_unsigned_monero_tx` → проверка и экран транзакции на
   устройстве → `1789839961_signed_monero_tx`.

Отказ устройства (чужой кошелёк, не синхронизированы key images, подмена
адреса сдачи, …) приходит двумя путями: ERROR на PUT, если файл не того
вида, и строкой LOG уровня error с подробностями, если файл отклонён после
разбора.

## 8. Сторона устройства

- `link.c`: inbox/outbox по слоту на вид файла (PSRAM), мьютекс между задачей
  линка и криптозадачей; состояние и маска приёма задаёт оболочка
  (`mw_link_set_state`), классификатор файлов и «будильник» интерфейса —
  `mw_shell_link_install()`.
- Когда открыт кошелёк, меню кошелька ждёт событий линка: PUT или REQ будят
  его, файл обрабатывается, затем меню показывается снова.
- `usb_link_arduino.cpp`: задача `usblink` на ядре UI читает `Serial`, кольцо
  HID-отчётов (128 отчётов, ~8 КБ внутренней RAM) и кольцо лога; отвечает тем
  же транспортом. Строки лога уходят с таймаутом 100 мс (ответы — 5 с), не
  уходят по HID, пока по HID приходит запрос, и между строками кольцо HID
  разбирается. Если COM-порт закрыт (нет DTR) или ядро не принимает байты,
  ПК на Serial считается ушедшим, и лог туда больше не идёт: раньше каждая
  строка держала задачу до 5 с, и HID-запросы в это время терялись.
  Переполнения кольца и отброшенные кадры пишутся в лог не чаще раза в
  секунду и только при изменении счётчиков.
- При загрузке в лог пишутся причина сброса и свободная внутренняя куча
  (всего и наибольший блок).
- PID `0x4024` (CDC + HID), `0x4025` (только CDC); при CDC On Boot ядро само
  задаёт PID `0x1001` — `mwlink.py` знает все три.

## 9. Программа на ПК

- `mwlink.py` — библиотека (`Wallet`, `Exchange`, транспорты, правила имён) и
  CLI: `ping`, `info`, `status`, `send`, `put`, `get`, `clear`, `request`,
  `console`, `exchange`.
- Выбор транспорта (одинаковый в CLI и окне): `--hid` / «hid» — только HID;
  без флагов / «auto» — HID, если установлен `hidapi` и у устройства есть
  HID-интерфейс (USB Mode = USB-OTG), иначе COM-порт, найденный по VID/PID;
  `--serial PORT` / выбранный в окне порт — этот порт, а если он занят другой
  программой (Arduino IDE, второй экземпляр) — HID. Программа пишет
  «connected over hid» или «connected over serial COMx».
- Обрыв связи (сброс устройства, кабель) — `LinkDisconnected`. CLI ждёт
  устройство до 10 с и печатает причину сброса из INFO; окно переподключается
  само каждые 2 с. Результаты, которые устройство сделало до сброса, потеряны
  (outbox в RAM) — файл нужно отправить снова.
- `mwlink_gui.py` — tkinter-фронтенд: подключение по HID/Serial, «Отправить
  файл…» (любой файл), наблюдение за папкой обмена, «Запросить адрес»,
  «Запросить данные view-only», автоматическое сохранение результатов,
  журнал устройства с фильтром отладочных строк и сохранением в файл.
  Private view key показывается в отдельном окне с кнопкой копирования и в
  журнал (и в «Save log») не попадает.
- Зависимости: `pip install pyserial hidapi`.
